# 毎日の号を作る

構造生物学者向けのニュースレター。毎日、査読済みのオープンアクセス論文のうち新しい構造を報告した論文を**すべて**、
要約・読みどころ・実験メモ・構造図を付けて紹介する。新しい構造以外でも、基準を満たした注目の構造（サイトの表記は Structure-Based Study）を最大 3 本加える。

**原則：数値・ID・リガンド・生物種は PDB / UniProt から機械的に取得し、手で書かない。
AI が書く文章の主張には、論文本文からの逐語引用を必ず付ける。**

## 手順

日付は特に指定がなければ、対象＝昨日（UTC）に Europe PMC に登録された論文、号の日付＝その翌日。
毎朝 9:07（日本時間）に実行すると、号の日付は今日（日本時間）になる。何時に実行しても同じ論文には同じ日付が付く。

1. **ブランチを作る**
   ```bash
   ISSUE=$(python3 -c 'from pipeline.common import default_issue_date; print(default_issue_date())')
   BRANCH=claude/issue-$ISSUE
   n=2; while git ls-remote --exit-code origin "refs/heads/$BRANCH" >/dev/null 2>&1; do BRANCH=claude/issue-$ISSUE-$n; n=$((n+1)); done
   git checkout -b $BRANCH
   ```
   同じ日付のブランチがすでにある（手動のテスト実行などで先に作られた）場合は `-2` などを付ける。
   その場合は PR の本文で、先にある PR と内容が重なっていないか（`candidates.json` の `index_date`）に触れる。

2. **候補を集める**（2〜5 分）
   ```bash
   python3 -m pipeline.collect --catch-up      # 日付を指定する場合: --index-date 2026-10-06（号の日付は自動で翌日）
   ```
   `data/issues/$ISSUE/candidates.md` に候補一覧、`.cache/packets/<PMCID>.md` に各論文の本文ができる。
   - `--catch-up` は、**論文のあった最後の号の翌日から昨日まで**をまとめて検索し、すでにどこかの号の候補に出た論文は除く
     （通常は昨日 1 日分と同じ。Europe PMC の遅れや前日の実行の失敗で飛んだ日があっても取りこぼさない）。
   - **期間が複数日になったときは、日ごとに号を分けて書く**（1 日 = 1 号 = 1 つの PR）。`collect` は期間の候補を登録日（索引日）で分け、
     `data/issues/<登録日の翌日>/candidates.json` を日の数だけ作る（候補のない日も空の号になる）。以降の手順 4〜7 は**日ごとに**行い、
     各号を別のブランチ `claude/issue-<号の日付>` に載せて、号ごとに PR を出す：
     ```bash
     git checkout -b $BRANCH origin/<デフォルトブランチ>      # 号ごと。手順 1 で作った作業ブランチから data/issues/<日付> だけを持ってくる
     git checkout <作業ブランチ> -- data/issues/<日付>
     ```
     すでに複数日にまたがる 1 つの号として書いてしまった場合は `python3 -m pipeline.split <号の日付>` で日ごとの号に分けられる
     （記事・採点・今日の一本を日ごとに振り分ける。`rank` は日ごとに振り直す。3 本以上ある日の今日の一本が空なら選び直す）。
     本数の上限はない（すべて記事にする）。
   - **Europe PMC が止まっているときは、自動で PMC のオープンアクセスデータ（AWS）に切り替わる**（`pipeline/pmcoa.py`）。
     Europe PMC は、その日に初めて索引された直近 2 週間のオープンアクセス論文が前 14 日の中央値の 1 割未満（または 50 本未満）
     だと「停止」と判定される（2026-10-11 から数日続いた実例がある）。この間も PMC 本体には新着が入り続けるので、
     NLM の公開バケットから、期間に書き込まれた論文の一覧→本文テキストで構造の語を絞る→合致した論文の XML を読む、の順で候補を作る。
     以降の手順（本文の読み方・記事の書き方・検証）は Europe PMC のときと同じ。
     この経路で作った号は `candidates.json` に `"source": "pmc-aws"` が付き、**画面のフッターに NLM の出典が自動で出る**
     （Europe PMC の号には出ない）。PR の本文に「Europe PMC が止まっていたため PMC のデータから作った」と一行書く。
   - **Nature 系の雑誌は出版の翌日に入る**（`pipeline/springer.py`、2026-10-18 から）：Crossref で前日（UTC）に出版された
     Nature Communications・NSMB・Communications Biology・Nature など 14 誌の論文を探し、オープンアクセスのものの全文を
     Springer Nature の Open Access API（JATS XML）から読む。環境変数 `SPRINGER_NATURE_OA_API_KEY` が要る（クラウド環境の設定。
     リポジトリには書かない）。キーがない・API が失敗した日は自動で飛ばし、その論文は従来どおり 1 か月ほど後に PMC から入る。
     この経路の論文には PMCID がないので、`pmcid` の欄に `SN-<DOI の記事番号>`（例：`SN-s41467-026-77727-2`）が入る。
     本文は同じく `.cache/packets/SN-....md`、記事のファイルは `picks/SN-....json`。あとから PMC に同じ論文が届いても
     DOI で除かれる（`candidates.json` の `springer.read`）。Scientific Reports は本数が多い（1 日約 150 本）ので従来の経路のまま。
     PR の本文に「Springer Nature の API から N 本」と一行書く。
   - **終了コード 3（`STALLED`）なら号を作らない**：Europe PMC が止まっていて、PMC（AWS）にも新着がない（または取得に失敗した）。
     何も書かれていない（`data/issues/` にも出ない）ので、手順 1 で作ったブランチは push せずに捨て、PR は作らず、
     `PushNotification` で知らせて終わる。`--source europepmc` は PMC への切り替えを禁じる試験用、`--source pmc-aws` は
     PMC を強制する試験用、`--force` は停止でも Europe PMC から集める試験用。
3. **編集者のフィードバックを読む**：`docs/style-notes.md` を読み、そこに書かれた方針に従う。
   GitHub のツールが使える場合は、直近の号の Pull Request に付いたオーナーのコメントも読み、
   今後も守るべき指摘があれば `docs/style-notes.md` に追記する（この号の PR に含める）。

4. **対象と順番を決める**：`candidates.md` の新しい構造の論文を**すべて**記事にする（**本数の上限はない**。
   2026-10-18 のオーナーの決定で「1 日 15 本まで」をやめた）。順番（`rank`）は下の「並べ方」で決める。
   0 本なら記事は書かず、手順 7 へ。
   **New Structure・Structure Update・Structure-Based Study の 3 部の分け方はサイトが自動で決める**（`render.part_of`、オーナーの決定 2026-10-18）：
   - **New Structure**：構造が**初めて解かれたタンパク質**の論文（論文のタンパク質のどれかに、それまで PDB の構造がなかった：
     `candidates.json` の `proteins[].first_structure`）。
   - **Structure Update**：それ以外の新しい構造の論文**すべて**（既に構造があるタンパク質の別の状態・リガンド・相手との複合体、
     EMDB のマップだけ、PDB ID を本文からたどれない論文）。
   - **Structure-Based Study**：手順 5b で選ぶ、既存の構造を使った研究（`"section": "impact"`、1 日最大 3 本）。
   - タンパク質を UniProt に対応づけられない論文（PDB が未公開、ID が本文にない）で、論文が「初めての構造」と書いているときだけ、
     その逐語引用を `first_claim` に書く（New Structure になる。`pipeline/schema.py`）。書いていなければ Structure Update。

5. **記事を書く**：論文ごとに `.cache/packets/<PMCID>.md` を**全体に目を通して**から
   `data/issues/$ISSUE/picks/<PMCID>.json` を書く。形式は `pipeline/schema.py` の `EXAMPLE`、
   書き方は下の「書き方」。既存の例：`data/issues/2026-10-07/picks/`。
   本文を読んで「実は既存構造を使っただけ」と分かった論文は、新しい構造としては書かず、手順 5b の採点に回す（PR の本文にそう書く）。
   `pipeline.verify` の最後に出る「記事のない新しい構造」の一覧は、すべて PR の本文で理由を説明する。

5a. **今日の一本を選ぶ**（記事が 3 本以上の日だけ）：下の「今日の一本」の手順で `feature.json` を書く。
   記事を書いたあと（手順 5・5b の後）に選ぶ。

5b. **注目の構造（新しい構造以外）を選んで書く**：下の「注目の構造」の手順で `impact.json` を書き、
   選んだ論文（最大 3 本）の記事を `"section": "impact"` 付きで書く。該当がなければ `impact.json` だけでよい。

6. **検証する**
   ```bash
   python3 -m pipeline.verify $ISSUE
   ```
   `[NG]` が出たら直して、全部 `[OK]` になるまで繰り返す。引用が見つからないときは、
   packet から一字一句コピーし直す（言い換え・省略・つなぎ合わせは不可）。

7. **描画する**
   ```bash
   python3 -m pipeline.render $ISSUE
   ```
   `data/issues/$ISSUE/README.md`（号のページ）と `figures/<PMCID>.svg`（タンパクの構造図。文字は入らない）、
   `figures/<PMCID>-thumb.svg`（一覧用のサムネイル。記事の図と同じ実際の PDB 構造を小さく描いたもの。構造がない記事には作らない）、
   `figures/<PMCID>.json`（図の凡例・リガンド・PDB ID。記事の凡例と 3D ビューアの色はここから作られる）ができる。
   リガンドがあれば、結合部位の拡大は `<PMCID>.svg` の右の枠に入る（別の拡大図は作らない）：4 Å 以内の残基をスティックで、
   水素結合と思われる組（リガンドとタンパク質の N・O が 3.5 Å 以内）を水色の点線、π 相互作用と思われる組（芳香環どうしの重なり・
   T 字、Lys/Arg と芳香環。PLIP の基準）を橙の点線で示し、**ラベルはその相互作用をしている残基だけ**に付く。
   膜タンパク質（UniProt に膜貫通領域がある）は、**膜の外側（細胞外・内腔・ペリプラズム）が上**になるように自動で立てて描かれる。
   今日の一本には、トップページ用の大きな構造図 `<PMCID>-hero.svg`（ラベルなし。トップの 3D ビューアが読み込まれるまでとスマホで出る）もできる。
   `figures/<PMCID>.json` の `view`（`hero_view`）は 3D ビューアの最初のカメラ（図と同じ向き）。

8. **コミットして PR を出す**
   ```bash
   git add data/issues/$ISSUE docs/style-notes.md
   git commit -m "Add issue $ISSUE"
   git push -u origin $BRANCH
   ```
   PR はリポジトリのデフォルトブランチに向けて作る。タイトル：`構造生物学デイリー $ISSUE 号`。
   本文の先頭に、見た目を確認するプレビューのリンク
   `https://shakewakame.github.io/Foldfeed/preview/$ISSUE.html`（PR を出してから 1〜2 分で表示される）を書く。
   続けて、選んだ論文の見出し、号のページへのリンク、候補数（`candidates.json` の `counts`）、
   **今日の一本に選んだ論文とその理由（`feature.json` の `reason`・軸・迷った論文）**——この理由はサイトには出ないので PR の本文が唯一の置き場、
   選ばなかった有力候補とその理由、`editor_notes` の要約を書く。
   PR を出すと GitHub Actions がプレビューを公開し（`pages.yml`）、編集者にメンション付きのコメントで知らせる（`notify.yml`）。
   確認待ちの号は `https://shakewakame.github.io/Foldfeed/preview/` に一覧で出る。記事が 0 本の日もプレビューは出る。
   `config/editorial.json` の `review_required` が `true` の間は**マージしない**（編集者が確認してマージする）。
   `false` なら、検証が通っていればマージする。

## 対象と並べ方

- 新しい構造の記事の対象は `kind` が `new_structure`・`new_structure_ids_unlisted`・`new_map_only` の論文**すべて**。
  `new_structure_ids_unlisted`（寄託したと書いてあるが、本文から PDB ID にたどり着けない論文）も**見送らずに記事にする**
  （オーナーの決定、2026-10-18）。PDB と照合できないので図は描かない（図なしの記事）。記事の冒頭の断り
  「論文の本文から PDB ID にたどり着けなかったため…構造図は載せていません」はサイトが自動で出すので、紹介文には書かない。
  手法と分解能は本文から `method_label` に書く。
  `uses_existing` と `no_ids` は、下の「注目の構造」の基準を満たしたものだけを記事にする。
- 号の中では、次の順に並べる（`rank` が小さいほど上）：
  1. **初構造**：そのタンパク質・複合体で初めての構造（`first_structure` が true、または論文が明言）
  2. **機構の解明**：構造変化・複数状態・触媒機構など、構造から「なぜ・どうやって」が分かる
  3. **創薬・モダリティ**：阻害剤・抗体・ペプチド・分解誘導剤などとの複合体
  4. **手法の工夫**：時分割、in situ、新しい安定化法など、他の研究者がまねできる工夫
  5. 生物学的に広く関心を集めるテーマ（病原体、ヒトの疾患関連、大型複合体）
- 同じ順位なら、上位にテーマが偏らないようにする（同じタンパク質ファミリーや同じ手法が続かないように）。
- 本文が途中で切れている（`[... truncated ...]`）論文も記事にする。読めた範囲で書き、`editor_notes` にその旨を書く。

## 注目の構造（新しい構造以外）

新しい構造ではないが、インパクトのある論文も記事にする（オーナーの決定、2026-10-12）。
対象は 4 種類：既存構造で機構を解明（`mechanism`）／構造予測・AI・デザイン（`ai_design`）／
新しい手法・ソフト（`method`）／構造に基づく創薬（`drug`）。1 日最大 3 本（**目安は 1〜3 本**。2026-10-18 に基準を 7 点→6 点に緩和）、記事の形式は新しい構造と同じ。
**実験で決めた構造（X 線・クライオ電顕・NMR。既存の PDB 構造を含む）で確かめた研究だけ**を対象にする。
MD・構造予測・ドッキングだけが根拠の論文は入れない（オーナーの決定、2026-10-12）。
基準の定義は `pipeline/impact.py`（ここを直せば基準が変わる）。

1. **ふるい分け**：`candidates.md` の「注目の構造の候補」を上から全部見る（題と要旨）。並び順と ⚠ は
   キーワードによる目安で、選定ではない。次は採点に進めない：
   MD・構造予測・ドッキングなど計算だけが根拠で、実験で決めた構造による裏付けがない／
   ドッキング・ネットワーク薬理学・免疫インフォマティクス・ADMET 予測だけで実験的な検証がない／
   総説・プロトコル集／構造が議論に関わらない臨床研究／生体高分子が主題でない。
2. **採点**：残った論文から最大 10 本を選び、本文（packet）を読んで 4 つの基準で採点する。候補が 5 本以上ある日は**最低 5 本**採点する
   （静かな日でも読まずに 0 本にしない）。
   - `novelty`（0〜3）何が初めてか：3＝分野の定説を変える／2＝明確に新しい／1＝既知の延長
   - `reach`（0〜3）誰に効くか：3＝構造生物学の分野全体／2＝大きなファミリーや広く使われる系・道具／1＝その系だけ
   - `structure`（0〜2）実験で決めた構造で結論を確かめているか：2＝実験構造なしでは結論が成り立たない／
     1＝実験構造で一部を確かめた（測った結果が既存構造の上で直接説明される、自前の NMR・HDX・架橋などの構造データがある）／
     0＝MD・予測・ドッキング・QM/MM など計算モデルだけ。**既存の PDB 構造を MD・ドッキングの出発点に使っただけなら 0**。**0 点の論文は選ばない**
     （AI・デザインの論文なら、設計・予測した構造を X 線・クライオ電顕・NMR で確かめていること）
   - `support`（0〜2）裏付け：2＝独立した実験で検証（変異体・機能測定・既存手法との比較）／1＝一部のみ／0＝計算のみ
   1 点以上を付けた基準には、その根拠となる文を packet から**一字一句**引用する。
   掲載誌の格は点数に入れない（読んだ内容で判断する）。
3. **選ぶ**：合計 **6 点以上**（10 点満点）かつ `structure` が 1 点以上、`novelty` が 2 点以上の論文を、点数の高い順に**最大 3 本**。
   同点なら種類が偏らないように選ぶ。6 点の論文は「その系だけの続報」になりやすいので、選ぶときは `reason` に何が新しいかを書く。
   基準を満たす論文がない日は 0 本でよい（数を合わせるために基準を下げない）。
4. **`data/issues/$ISSUE/impact.json` を書く**（採点したすべての論文。選ばなかった論文も残す）：
   ```json
   {"screened": 22,
    "scored": [{"pmcid": "PMC…", "type": "mechanism", "scores": {"novelty": 3, "reach": 2, "structure": 1, "support": 2},
                "selected": true, "reason": "選んだ／選ばなかった理由を日本語 1〜2 文",
                "evidence": {"novelty": [{"quote": "…", "section": "Abstract"}], "reach": [...], ...}}]}
   ```
   `screened` はふるい分けで見た本数。
5. **記事を書く**：選んだ論文ごとに、新しい構造と同じ形式の `picks/<PMCID>.json` を書き、`"section": "impact"` を付ける。
   - `rank` は注目の構造の中での順（点数の高い順）。ページでは「新しい構造」と「注目の構造」が見出しで区切られ、
     注目の構造は新しい構造の後にまとまって出る。
   - `method_label` に手法（例：`HS-AFM・電気生理・粗視化MD`）を書く（欄外の Method に出る。構造の手法名は `Cryo-EM`・`X-ray` のように英語）。
   - 構造図は論文が使った既存の PDB 構造から描く。`ga_pdb_id` で選ぶ（省略時は `cited_structures` の最初）。
     PDB 構造を使っていない論文（AI・手法など）は構造図なしになる。
   - タグに `初構造` は使えない。見出しや要約で「新しい構造」と誤解させない（「既存の構造を使って」と明記する）。
6. `pipeline.verify` が `impact.json` も検証する（引用・点数の範囲・6 点以上・structure 1 点以上・novelty 2 点以上・3 本以下・記事との対応）。
7. PR の本文に、選んだ論文と点数、選ばなかった上位の論文と理由を書く（`README.md` 末尾の採点表と同じ内容でよい）。

## 今日の一本（サイトの表記は Today’s Structure）

その日の記事（新しい構造と注目の構造を合わせて）から 1 本を、トップと号の頭に大きく出す。記事が 3 本未満の日は選ばない。
選ぶ基準は 3 つの軸のどれかが突出していること：構造生物学（構造から新しい機構・状態・結合様式が分かる）／
生命科学（生物学的な問いに答える）／創薬（薬の標的・結合部位・耐性・療法の設計に直結する）。

1. その日の記事を比べて 1 本を選ぶ。掲載誌の格や話題性ではなく、論文が実際に示したことで選ぶ。
   迷った論文があれば `considered` に理由を書く。
2. `data/issues/$ISSUE/feature.json` を書く：
   ```json
   {"pmcid": "PMC…", "axes": ["structure", "biology", "drug"],
    "reason": "選んだ理由を 100 字以内で。論文が示したことだけで書き、「画期的」などは使わない。",
    "evidence": [{"quote": "理由を支える、論文本文からの逐語引用（英語のまま）", "section": "Abstract"}],
    "considered": [{"pmcid": "PMC…", "note": "最後まで迷った論文と、選ばなかった理由"}]}
   ```
   `axes` は `structure`（構造生物学）・`biology`（生命科学）・`drug`（創薬）から、突出しているものだけ。
3. `pipeline.verify` が `feature.json` を検証する（記事にあるか・軸・引用が本文にあるか・理由の長さ）。
4. **選んだ理由はサイトの記事には出さない**（トップの「今日の一本」には見出し・補足・構造図だけが出る）。
   理由は `feature.json` と号の `README.md`、そして **PR の本文**に書く：選んだ論文とその理由、迷った論文。
   編集者は PR のコメントで差し替えを頼める。

## 書き方

- **画面に注釈・補足説明・断り書きを書かない**（編集者の指示 2026-10-14）。サイトに出る文章は、見出し・紹介の4〜5行・読みどころ・実験メモ・原文の引用など、論文の中身だけにする。
  「〜の日は論文が少ない」「この欄は〜のためのもの」「このブラウザにだけ保存」のような注意書き・説明文は、画面ではなく PR の本文か docs に書く。

- **常体（だ・である調）**で簡潔に。体言止めは使わず、主語と述語のある**ふつうの文**で書く。
- **初めて読む人にも筋が追えるように書く**（2026-10-14 編集者の指示）。読者は構造生物学者だけとは限らない。
  その論文のカギになる語（例：二量体化、ゲートヘリックス、Treg、ニトロ化）は、**初めて出る行の中で**「〜（それが何か）」と短く言い換える。
  「Wzt の二量体化の準備になる」のように、それが何のために起こるのかが書かれていない文は不完全。**なぜそれが大事か**まで、その行の中で書く。
  説明は注釈（※）や脚注にせず、文の一部にする。説明のための言い換え・ごく軽い解釈（「〜という膜のタンパク質」「〜するスイッチ」程度）は許す。
  ただし**論文にない事実・数値・意義を足さない**。論文の著者が推測と書いたことは「〜と考えられる」「〜可能性がある」と書く。
- 用語は日本語の定訳＋必要なら略称（クライオ電顕、副溝、膜貫通ヘリックス）。タンパク質名・遺伝子名・
  残基番号・化合物名は論文の表記に従う。
- **数値**は論文本文か PDB にあるものだけ書く。分解能を書くときは PDB の値を優先する。
- **誇張しない**。「初めて」は `first_structure` が true か論文が明言している場合だけ。
  著者の解釈・推測は「〜と考えられる」「〜を示唆する」と書き分ける。著者自身が書いている限界
  （人工コンストラクトである、分解能が低い部分がある等）は省かない。
- 各フィールドの役割と上限文字数（`pipeline/schema.py` の `LIMITS`）：
  - `headline`（主見出し、36 字以内）と `subhead`（補足、64 字以内）：一覧とトップに「構造図・主見出し・補足」で並び、
    記事では構造図の直後に出る（記事のページの見出しは論文の原題）。
    **主見出しは発見の面白さを先に見せる短い一文、補足は構造や手法の言葉で具体的に**。例：
    主見出し「基質とATPで構造が切り替わる、結核菌のガラクタン輸送体」／補足「3つの状態をクライオ電顕で解析。ゲートヘリックスの動きが輸送のカギを握る」。
    **論文が支持する範囲だけで書く**：その記事の `highlights`・`summary`（どちらも根拠の引用つき）が言っていることだけを使い、
    「初めて」「世界初」「画期的」「〜を解明」など、著者が言っていない強い言葉は使わない。著者が推測・可能性として書いたことは
    「〜可能性」「〜らしい」と書く。主見出しや補足に出る名前・略号・数値は、論文の本文かその記事の要約・読みどころにあるものだけ
    （`pipeline.verify` が機械的に照合する）。
    **日本語として自然に書く**（2026-10-13 に編集者から「少し変な日本語」と指摘された）。書いたあとに声に出して読んで確かめる：
    - 主見出しは「〜は、〜する」「〜が、〜を〜する」の**ふつうの文**にする。主語を落とした断片（「結合する場所で、〜」）、
      コロンでつないだ見出し（「A：B」）、名詞を並べただけの句は避ける。語順は日本語の自然な順に。
    - 「基質が来ると」のような口語、「足場に係留される」「切断を捉える」のような**言葉の組み合わせが不自然な直訳**は使わない。
      迷ったら動詞を簡単にする（結びつく・結合する・認識する・外れる・入り込む）。英語の動詞を直訳しない。
    - ホームと号の一覧は**カード（構造図・Target・見出し・補足だけ）**なので、見出しと補足の 2 つだけで
      「何の構造で、何が分かったか」が伝わるように書く（4 行の紹介は記事を開いたときにだけ読まれる）。
    - 補足は**一文として完結させる**。「〜の構造。差はMDで現れた」のような体言止めの断片のつなぎ合わせではなく、
      「〜の結晶構造では差が小さく、違いはMDで現れた」のように述語まで書く。用語の羅列にしない。
    - 論文に書かれた略号（dIII、WIN 部位など）は、読者が構造生物学者として知っているものだけ主見出しに使い、補足で補う。
  - `target_label`（30 字）：標的の短い表記（例：`SpNanR（肺炎球菌）`）
  - `target_en`（52 字）：**標的の英語表記**。記事の TARGET 欄と、カード・Picked up Today’s Structure の Target に出る
    （例：`SpNanR (S. pneumoniae)`、`AMPA receptor GluA2–γ2`、`Human OCTN1 (SLC22A4)`）。`target_label` を英語にしたもの。
    生物種はよく知られた略記（`E. coli`、`M. tuberculosis`）でよい。日本語を入れない（`pipeline.verify` が確かめる）
  - `summary`：記事の頭に出る**4 行の紹介**。順に `question`（疑問・課題、80 字）・`approach`（アプローチ、80 字）・
    `result`（結果、90 字）・`learned`（わかったこと、100 字）。**一行は 1〜2 文**。上限いっぱいに詰めず、60〜70 字で収まるなら収める。
    4 行は**一つの流れ**として読めるように書く（疑問 → 方法 → 見えたこと → だから何が言えるか）。
    - **論文が言っていないことは絶対に書かない**。論文の言葉を言い換えるのは、読者が誤解しない範囲でだけ。
      推測は推測と書く（「〜とみられる」「〜可能性がある」）。著者が「示唆」「提案」と書いたことを断定にしない。
    - `question` は論文の Introduction／Abstract が「分かっていなかった」「不明」と書いていること。
      論文にそう書いていなければ、論文が挙げた課題（「〜が必要だった」「〜と予想された」）をそのまま使い、「未解明だった」と補わない。
    - `result` は観察と数値、`learned` はそこから論文が結論していること（読者に一番残したい一文）。
    - **各行に根拠の引用が必要**：`summary.evidence.question / approach / result / learned` に、packet から**英語のまま一字一句**コピーした
      20 字以上の文を 1〜2 個ずつ（Abstract と Introduction の文で足りることが多い）。`pipeline.verify` が本文との一致と、
      各行の名前・略号・数値が論文にあることを機械的に確かめる。
    - 引用の文は画面には出ない（号の `README.md` に「この紹介文の根拠」として出る。編集者が見る）。
    - **任意の 5 行目 `open`（残された課題、80 字）**：論文自身が「まだ分からない」「今後の研究が必要」「限界」と書いていることがあるときだけ
      書く（Discussion・Limitations・Conclusion の文）。書いていなければ**この行ごと省く**（FoldFeed 側の推測で埋めない）。
      これにも引用が必要（`summary.evidence.open`）。
  - `categories`（1〜3 個）：タンパク質の種類。`pipeline/schema.py` の `CATEGORIES` から選ぶ
    （kinase・protease・receptor・channel・transporter・enzyme・nucleic・chromatin・translation・regulation・immune・pathogen・
    photosynthesis・other）。ホームの「タンパク質の種類から探す」と `proteins.html` に使われる。迷ったら主役のタンパク質の働きで選ぶ。
  - `topics`（任意、0〜3 個）：研究の種類。`pipeline/schema.py` の `TOPICS` から選ぶ（design デノボデザイン・drug 創薬・阻害剤・
    antibody 抗体・ナノボディ・ai AI・構造予測・membrane 膜タンパク質・dynamics 構造変化・中間状態・insitu in situ・トモグラフィー・
    method 手法の開発）。ヘッダーの検索の「Research Type」に使われる。**書かなければサイトが題名・要旨・記事の文から自動で付ける**ので、
    自動の判定がずれるとき（例：AlphaFold を道具として使っただけなのに「AI」になる、設計したタンパク質なのに「デノボデザイン」が付かない）だけ書く。
    書くと自動の判定は使われない（`[]` で「なし」）。論文が主題にしていることだけを選ぶ
  - `highlights`（1〜3 個、各 200 字）：「読みどころ」として出る。タグは `初構造・新しい結合部位・機構の解明・創薬・モダリティ・手法の工夫・実験Tips`
    だが、画面には表示しない（内部の分類。将来の絞り込み用）
  - `lab_notes`（各 160 字）：Methods に書いてあることだけ。書いていない項目は `null`
- **evidence（根拠の引用）**：highlights の各項目に 1〜2 個、lab_notes に必要な数だけ。
  packet から**英語のまま一字一句**コピーした 20 字以上の連続した文（1〜2 文）。`section` には見出し名を書く。
- 欄外の表示と構造図用の任意項目：
  - `ligand_label`：結合分子を略号（BMX など）ではなく分かる名前で（例：`ManNAc-6-P（BMX）`）
  - `method_label`：PDB 情報がない論文（ID が補足資料のみ）で、本文にある手法と分解能（例：`Cryo-EM・全体 2.8 Å`）。
    **手法名は英語**で：`Cryo-EM`、`Cryo-ET`（トモグラフィー・サブトモグラム平均）、`X-ray`、`NMR`、`MicroED`。
    PDB 情報がある論文は自動で同じ表記になる（サブトモグラム平均のエントリは `Cryo-ET`）
  - `ga_pdb_id`：構造図に使う PDB ID（省略時は最高分解能の構造）。論文の主張を一番よく表す構造を選ぶ
  - `legend_labels`：構造図の凡例（タンパク質・核酸）の名前を、`figures/<PMCID>.json` の `legend` と同じ順に日本語で上書き。
    初学者がこれだけで何のタンパク質か分かるように「GPR84（受容体）」「Gαi1（G タンパク質 α）」「ヒストン H3」のように、
    名前＋役割を短く。凡例の下には PDB の英語名が小さく出る。遺伝子名が `LOC…` や `S` のように分かりにくい場合、
    タンパク質が複数ある複合体、DNA・RNA の鎖は**必ず**書く（`python3 -m pipeline.render` を一度回して `legend` の順と数を確認してから）。
    役割は PDB の名前と論文本文にあることだけで書く
  - `ligand_names`：構造図のリガンド（スティック表示）の凡例名を `{"化合物ID": "表示名"}` で。論文での呼び名を使う
    （例：`{"A1CKT": "OX04529", "U1C": "ダントロレン"}`）。ATP・NADP+ などよくある分子は自動で略号になるので不要。
    `python3 -m pipeline.render` の後、`figures/<PMCID>.json` の `ligands` に ID のまま・長い化学名のままの
    ものがあれば追加して描き直す
  - `site_ligand`：結合部位の拡大図に使うリガンドの ID。省略時は `ligand_names` の最初のリガンド、なければ
    最も大きいリガンド。論文の主役でないもの（緩衝液成分や結晶化剤）が選ばれたら指定し直す。`""` で拡大図なし
  - **構造図は、各タンパク質・リガンドを引き出し線で名指しする**（2026-10-14）。`legend_labels`（「Wzm（膜貫通）」のように
    名前＋役割。括弧の中が小さく下に出る。**役割は 10 字前後**。長いと「…」で切れる）を書いたタンパク質、`ligand_names` を含む
    リガンド（最大 4 種）に線が引かれる。`legend_labels` を書かないタンパク質には線が引かれないので、**主役のものは必ず書く**。
    リガンドがあれば、結合部位の拡大図が図の右に枠つきで並び、全体図の該当箇所が破線の円で結ばれる
    （拡大図の点線：水色＝水素結合、橙＝π 相互作用。残基のラベルは相互作用している残基だけ）。
  - `figure_notes`：論文が名指ししているドメイン・ヘリックスなどを、図の上で朱色にして線で名前を付ける。
    `[{"title": "ゲートヘリックス", "sub": "Wzt の一部", "entity": 2, "range": [23, 46]}]`（`entity` は凡例の何番目か、1 始まり。
    `range` は論文の残基番号＝PDB の auth 番号）。残基の範囲は論文本文の記述で裏づけ、`figure_evidence` に引用を書く。
  - `compare`：**論文が見つけたことを説明する比較図**（2026-10-14）。同じ複合体の 2〜3 個の PDB エントリ（開いた状態と閉じた状態、
    apo とリガンド結合、基質結合と ATP 結合など）を 1 つのタンパク質で重ね合わせ、同じ向きで並べ、`figure_notes` の最初の部分を朱色にする。
    `{"panels": [{"pdb": "25IN", "title": "基質結合型"}, {"pdb": "25IO", "title": "ATP 結合型"}], "align": 1,
    "mark": {"entity": 2, "residue": 36, "text": "約40 Å"}}`。`mark` は動きを矢印で示す残基（論文が距離を書いているときだけ。
    `text` の数値は論文にあるもの。`pipeline.render` が重ね合わせの実測距離と 25% 以上違うと警告する）。
    `align` は重ね合わせに使うタンパク質（凡例の何番目か）。パネルのタイトルは 16 字以内。**図が主張の説明になるときだけ付ける**
    （どの記事にも付けるものではない。「新しい構造」の記事で、論文の中心が構造の違いのときに）。
    記事ページでは凡例の下に並ぶ（ホームの Picked up Today’s Structure には記事の全体の図だけが出る）。
  - スマホ用の縦長の図（`figures/<PMCID>-m.svg`、比較図は `-compare-m.svg`）は `pipeline.render` が自動で作る。`legend_labels`・`ligand_names`・`figure_notes` の文字がそのまま使われる。
    **ラベルの文字は短く**（名前は 6 字前後、役割は 10 字前後）。長いとスマホの図で「…」で切れる
  - `figure_evidence`（`figure_notes`・`compare` を付けたときは**必須**）：残基の範囲、構造の違い、距離を支える論文本文の逐語引用。
- `editor_notes`：確信が持てない点、分類の判断、編集者に見てほしい点。
